# GRQ-010 Document creation → `backend/tests/acceptance/documentCreation.test.js`

> Scope (2026-11-23): what staff get when the server's own access to the file storage service (Google Drive) has
> expired or was revoked. Creating an edition is only the trigger that makes the system create documents: nothing
> else about editions is tested here. Document creation itself is tested with each use case that creates documents.

## Requirement
- GRQ-010 Document creation (`srs-export.txt` ~line 720): "The system shall be able to automatically create
  documents or copies of them, and share them to whom it may concern."
- NFRQ-015 Media storage integration (~line 3495): "The system shall integrate with a file storage service to manage
  uploaded videos, presentations, podcasts, catalogues, images, and supporting documentation."
- UC-029 Create edition (~line 1260): "The designer introduces the edition's information. The system will create the
  edition's master seed template document."
- No pending change in `srs-changes.md`.
- The SRS doesn't say what happens when the file storage service refuses the server. User's decision (2026-11-23,
  #311; private until released):
  - The request fails with `503`: the service the server depends on is unavailable. It is not `401`, because the
    user's own session is fine.
  - The error message tells staff that Google Drive access must be re-authorised.
  - Production answers the same `503` and message: it is not turned into the generic error for unexpected failures.
  - Lists that show images from the file storage still answer, without the images.

## Clarifications
- `docs/project/clarifications/general.md`: "Actors", "HTTP meaning", "Edition states".
- "HTTP meaning" keeps `401` for a guest and `403` for a logged-in user without permission. A designer with a valid
  session must get neither here.

## Vocabulary
- Trigger = creating an edition: `POST /editions` with `{ name, year }`, as `designer(1)`.
- "Drive access expired" = `revokeDriveAccess()` for the testing app; `productionApp({ driveAccess: 'revoked' })` for
  a production instance (`HELPERS.md`, "When the server's Drive access has expired" and "Production instance").
- Re-authorise message = the body's `error` names Google Drive and asks for it to be re-authorised: it contains
  `Drive` and matches `/re-?authori[sz]/i`.
- Generic error for unexpected failures = `{ "error": "Internal Server Error", "errorId": "<id>" }`.
- Staff see not-announced (`PLANNED`) editions in `GET /editions` ("Edition states").

## Test cases
Testing app
- **B1** Drive access expired: a designer creates an edition → `503`, not `401` or `403`; the body's `error` is the
  re-authorise message.
- **B2** After B1's request, no edition was created: `GET /editions` as the designer doesn't list it, and the fake
  Drive has no new file (`driveFiles()` has the same length as before the request).
- **B3** After B1's request, the designer's session still works: `GET /editions` with the same client → `200`.
- **B4** Drive access expired: a guest lists editions while an announced edition with a logo exists → `200`; that
  edition is listed and its `logo` is `null`.
- **B5** Drive access works again (`restoreDriveAccess()`): a designer creates an edition → `201`. This shows the
  `503` of B1 comes from Drive access, not from the request.

Production instance
- **B6** Drive access expired: a designer creates an edition → `503` with the re-authorise message; the body has no
  `errorId` and its `error` is not `"Internal Server Error"`.

## Fixture notes
- Restore Drive access after each testing-app test that revokes it (`afterEach`): a revoke lasts until the file
  ends.
- B4: arrange the announced edition with `anEdition` (logo by default) before revoking access.
- B6: start one production instance in `beforeAll` with `driveAccess: 'revoked'`, and stop it in `afterAll`. Its
  `as(user)` gives the designer's client.
- Use a different edition name in each create request, so each case stands on its own.
